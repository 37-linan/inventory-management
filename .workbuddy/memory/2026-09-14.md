## 扫码排查：出入库台账 vs 产品信息表（结论：同一套代码，勿再换算法）
- 核实: 所有扫码入口都调用 products.js 的 `triggerBarcodeScan(inputId)`
  - 产品信息表 添加物品 📷 → triggerBarcodeScan('product-code')
  - 入库单 扫码 → triggerBarcodeScan('inbound-order' / 'inbound-code')
  - 出库单 扫码 → triggerBarcodeScan('outbound-code' / 'outbound-order-no')
  - 补单号 扫码 → triggerBarcodeScan('fill-order-no')
  - 全部 → BarcodeScanner.startScan()（barcode.js，全站唯一扫码模块）
- 服务端 /home/ubuntu/inventory-app/public/js/modules/barcode.js 与本地 MD5 一致 (4bc5431738aae7fc9394d7c53d3575b5)
- 唯一能造成"同代码不同效果"的是分支：startScan 用 4s 超时竞速 getUserMedia
  - 相机开 → 实时视频(640x480 抽帧 + 逐帧解码) ← 准确率低
  - 相机失败/超时 → _startPhotoScan(系统相机拍照 + 服务端 ZXing) ← 准确率高
- iPhone 限制: Safari BarcodeDetector 对商品条码(EAN-13)支持差，实时路径实际靠 Quagga 硬扛

## 「待行情」根因 + 单利润弹窗内「补录行情」（2026-09-14）
- 用户问题：单号 3402275270422140970（出库日 2026-09-05）显示亏损 -62.10，
  因为 2 件商品（012547339468 李施德林口喷 / 4524734500804 LaboLabo 洁面乳）当时没录行情 → 销售额按 ¥0 算
- **根因（查 DB 确认）**：`main_price_history` 里这两个编码只有 `2026-09-14` 一条记录。
  order-profit 取价规则是「出库次日(09-06)优先 → 否则 date <= 出库日(09-05) 的最近一条」，
  09-14 > 09-05 属**"不往后找"**，所以取不到价 → 0
  - 对比吉列 6900068000520 / 护舒宝 6903148222539：它们有 08-18、08-26 的价，
    所以回退命中 08-26（截图里"次日: 2026-08-26"其实是**回退到的实际取价日**，不是字面次日）
- **修法（给用户的话术）**：给这两个编码补一条行情，日期填 **出库日 2026-09-05**（走回退分支）
  或 **09-06**（走次日优先分支）都行，值一样结果一样
- **新增功能**：单利润明细弹窗里，每个已出库商品后面加按钮
  - 缺价 → `补录行情`（btn-primary）；已有价 → `改行情`（btn-secondary）
  - 点开 → `_showBackfillPrice(idx)`：日期默认**自动带出库日**，可改成次日；价格输入 → 保存

    然后清 `_dashData` 缓存并重新打开单利润弹窗，数字立即重算
  - 实现要点：明细缓存在 `this._profitDetail` / `this._profitOrderNo`，按钮只传**下标**，
    避免把商品名/单号拼进 onclick 引发转义 bug（商品名常含引号/特殊字符）
